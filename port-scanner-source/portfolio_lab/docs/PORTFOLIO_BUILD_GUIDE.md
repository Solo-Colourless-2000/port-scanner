# ポートフォリオ制作手順（自分で実施するための作業書）

## 0. 本書と自作作品の境界

原典ZIPは書籍サポート用の演習素材です。このフォルダの `scanner.py` とテスト群は、このマニュアルの制作例として作った**別実装の見本**であり、このままコピーしても読者自身の開発実績にはなりません。公開前には元のリポジトリのREADME「サンプルコード」を確認してください。特に原典コードの大部分の転載や販売・配布には許可が必要と記されています。書籍サンプルの丸ごとコピー、元ZIP、脆弱なDockerラボ、第三者情報は自分の公開用GitHubリポジトリに入れないでください。公開内容は自分の記述・テスト・設計判断に限定します。

## 1. 開発のゴールと合否条件

作るのは脆弱性診断ツールではなく、指定したTCPポートへ接続を試みる小型CLIです。最初の受け入れ条件は、(a) 省略時に127.0.0.1のみ、(b) 不正なIP・空ポート・重複ポートを拒否、(c) スキャン対象外へ通信前に停止、(d) 開放・拒否・時間切れ・到達不能をOSからの観測に基づき分類、(e) JSONに日時と対象と結果を記録、(f) 既存の証拠ファイルを上書きしない、(g) 外部ネットワークへの実接続なしで異常系をテスト、の7つです。

### 目的にしないこと

このCLIはサービスの脆弱性、通信暗号化の安全性、OSの種類、認証の強度、攻撃可能性、接続経路の全体像を判定しません。「open=安全」「refused=完全遮断」「timeout=filtered」も断定できません。権限のある環境に限って使用します。`--authorized` は利用者の申告であり、許可を取得・照合する機能ではありません。

## 2. 作業フォルダと最初のGit操作

ZIPの展開先に移動後、`portfolio_lab/` があることを確認します。実際に自力で制作する場合は、完成見本とは別の**自分の作業用ディレクトリ**を作成し、そこへ手入力してください。既存の完成見本を初期コミットしても独自作品にはなりません。

```sh
pwd
ls -la portfolio_lab
mkdir -p my_tcp_connect_portfolio
cd my_tcp_connect_portfolio
git init
printf '# My TCP Connect Audit\n\n自分の設計・実装範囲をここへ記録。\n' > README.md
printf '__pycache__/\n*.pyc\n.venv/\nreport-*.json\n' > .gitignore
git add README.md .gitignore
git diff --cached --check
git commit -m "docs: define initial scope and evidence rules"
```

上の例では `git commit` に事前の `git config user.name` と `user.email` が必要な場合があります。`mkdir`、`cd`、`printf`、`git add` は他のファイルを作ったり追跡するため、対象ディレクトリの確認を先に行います。公開するコミットに本名や個人メールが入るかは自分で決めてください。

## 3. 開発の順序とコミットの切れ目

1. **入力検証**: `parse_ports()` と `check_scope()` を設計し、許可された値と不許可の値をテストする。テストを先に書いて失敗を確認すると、後から成功理由を説明できる。
2. **TCP観測**: `probe()` にIPv4/TCP接続、タイムアウト、例外処理を作る。`connect_ex()` は通常0またはOSのエラーコードを返し、`TimeoutError` が直接投げられる場合も考慮する。`TimeoutError` が `OSError` のサブクラスであるため、専用捕捉を先に置く。
3. **結果の説明**: `errno` と `state` を別に出力する。`errno` はOS依存であり、結果が不明なら不明のまま残す。
4. **JSON化**: UTCの時刻、対象、スコープ、試行したポート、タイムアウト、各結果を出力する。公開する前に対象IPなどを削る。
5. **CLI化**: `argparse` で必須・任意の引数、範囲、エラーの終了コードを設計する。
6. **ファイル保存**: `Path.open("x", encoding="utf-8")` で既存ファイルを上書きしない。ディスク不足などで途中書き込みが失敗すれば部分ファイルが残り得るため、運用版では一時ファイルと原子的な公開処理を別途検討する。
7. **CI**: `python -m unittest discover -s tests -v` をGitHub Actionsで実行し、失敗ログも残す。外部Actionのバージョンは導入時に再確認し、リポジトリ権限は必要最小限にする。

コミットは「機能とそのテスト」の組を基本とします。コミット名の例は `feat: classify TCP connect outcomes`、`test: cover timeout without errno`、`docs: record safe lab evidence` です。実施していない機能をコミット名やREADMEに書かないでください。

## 4. 動作実演（所有PCのloopbackに限定）

**端末A**を開いて、サーバーを起動します。

```sh
python3 -m http.server 8765 --bind 127.0.0.1
```

**端末B**で、`portfolio_lab/` を作業ディレクトリとして実行します。

```sh
pwd
python3 --version
python3 -m unittest discover -s tests -v
python3 scanner.py --help
python3 scanner.py --target 127.0.0.1 --ports 8765,8766 --timeout 0.5
```

サーバーが8765番で待ち受けていれば通常 `open`、ほかに8766番を使用するプロセスがなければ通常 `refused` になります。端末Aで `Ctrl+C` によりサーバーを停止したあと、同じスキャンを行います。TCP通信の成功・失敗は時刻・OS・ファイアウォール・ほかのプロセスの影響を受けるので、「どんな端末でも絶対にこの結果」とは書かないでください。

JSON保存例：

```sh
python3 scanner.py --target 127.0.0.1 --ports 8765,8766 --output evidence-local.json
python3 scanner.py --target 127.0.0.1 --ports 8765,8766 --output evidence-local.json
```

2回目は既存ファイルへの書き込みを拒否します。`--output` を含め実行したコマンド、終了ステータス、標準出力・標準エラーを区別して記録します。公開前にIPアドレスやローカルパスの扱いを確認してください。

## 5. 再現できる異常系を作る

時間切れを確かめるために第三者のIPへ長時間スキャンする必要はありません。`tests/test_scanner.py` の `ProbeErrorTests` はモックでソケット関数を差し替え、`TimeoutError()` と `errno.ENETUNREACH` を起こします。コネクション先として引数を渡しても、モック中はOSへTCP接続を行いません。`test_timeout_exception_without_errno` が成功したことだけで、現実のネットワーク機器がタイムアウトを必ず同じ方式で返すとは証明できません。

## 9. 面接での説明構成（2分）

- **背景**: ネットワークのポート状態は「開いている」「拒否」「応答がない」など異なる観測であり、単一の失敗として扱うと判断を誤る。
- **設計判断**: 誤操作を減らすため既定値をloopbackにし、CIDRと申告フラグの両方がなければローカルネットワークへ広げない。フラグは管理者からの正式な許可を代替しない。
- **実装**: Python socketの `connect_ex()` の戻り値と `TimeoutError` 例外を区別して分類、JSONに根拠を残す。
- **検証**: loopbackの実待受2件、外部通信しない例外テスト、入力の境界値、ファイル上書き拒否を確認。
- **限界**: セキュリティホールの有無、サービス同定、外部ネットワーク上の安定した結果を保証しない。プライベートIPでも許可なしに触れない。
- **自分の寄与**: 例から自分で追加した機能の要件・コードの差分・テスト・失敗と修正を具体的に説明する。
