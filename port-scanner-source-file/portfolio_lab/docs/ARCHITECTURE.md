# アーキテクチャ・設計判断（見本）

## 問題設定

学習用TCPスキャナは、TCP接続成功を観測できる一方、「接続に失敗した理由」を単に `closed` として扱うと意味が変わってしまう。原典 `code/chapter02/tcp-connect-scan-by-socket.py` の `connect_ex` の使用と比較し、結果の種類をあえて限定的に分類する。

## 処理の流れ

`CLI引数 → parse_ports → check_scope → probe (portごとに直列) → JSON出力`。

`parse_ports` は 1〜32件・1〜65535・重複なしの整数リストに制限。`check_scope` は初期値でloopbackのみ許可。ラボアドレスへ広げるにはCIDRと明示オプションを併用する。`probe` は接続成功・拒否・時間切れ・到達不能・その他のOSエラーを区別する。

## 判断の理由

* **対象範囲を明示**：コマンド誤入力による第三者スキャンを防ぐため。`--authorized` は許可の技術的証明ではないため、記録された管理者承認が別途必要。
* **直列/32件上限**：デモ用であり速度より再現性・低負荷を優先。スキャン時間の上限は全体タイムアウトではなく各ポートのタイムアウト×件数で変わる。
* **文字列を直接DNS解決しない**：別名解決やリバインディングなどのスコープ逸脱を避け、IPv4リテラルのみ受け付ける。
* **状態を5値で返す**：`timeout` を `filtered` と断言せず、`refused` と区別。OSごとのerrnoの違いは課題として残す。
* **JSON**：機械処理しやすく、発見日時と検査スコープも同時に保存できる。既存ファイル上書きを拒否する。

## 限界

TCPサービスのバナーやアプリケーション層は検査しない。UDP、IPv6、複数ホスト、並列実行、リトライ、パケットキャプチャ、脆弱性検出も行わない。許可・対象管理を完全に自動化したものではない。
